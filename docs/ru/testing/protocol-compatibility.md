# Совместимость протокола

Envelope и social object используют schema version `1`. Unknown/malformed input
отклоняется, подписи используют strict schemas, а canonical JSON сортирует keys,
поэтому порядок полей не меняет signature/action hash.

Совместимость со старой schema пока не обещана: новая версия потребует явной
migration/compatibility проверки, а не будет молча считаться version `1`.

Unit suite содержит фиксированные vectors для v1 canonical JSON и BLAKE2b-256
action hash. Их изменение требует намеренного решения о версии протокола.

## Canonical JSON v1: известные свойства

`canonicalJson` в `packages/core/src/crypto.ts` — формат v1. Его поведение
зафиксировано векторами в `crypto.test.ts`, включая тест, который запускает
функцию в отдельных процессах под локалями `C`, `ru`, `lt`, `da`, `et` и `tr`.

- **Порядок ключей** — ICU-коллация `en` (`localeCompare(b, 'en')`), а не
  порядок кодовых единиц UTF-16: `a` < `A` < `b`, `_x` перед цифрами. От
  локали ОС он больше не зависит. До ноября 2026 года зависел, поэтому объекты
  с не-ASCII ключами, подписанные под не-английской локалью, теперь могут дать
  другой хэш; инструментированный прогон тестов Core не нашёл не-ASCII ключей
  в подписываемых данных. Порядок по-прежнему зависит от ICU, и реализации на
  других языках пришлось бы воспроизводить его точно.
- **Поля со значением `undefined`** сериализуются как `"key":undefined` — это
  не JSON. После передачи через JSON поле исчезает, байты у получателя другие,
  и проверка подписи не проходит. Такие поля найдены в подписываемых объектах
  (например, `payload.thumbnailUri` и `payload.publishedAt` в Video/Shorts,
  `parentWorkerId` в agent workers).
- **Не-JSON значения** теряют данные: `Date` и `Map` становятся `{}`,
  `NaN`/`Infinity` — `null`, `-0` — `0`, typed arrays — объектами с индексными
  ключами. В подписываемых данных тестов Core их не встретилось.
- Строки не нормализуются по Unicode; одиночные суррогаты экранируются, как в
  `JSON.stringify`.

## Canonical JSON v2

`canonicalJsonV2` в `packages/core/src/crypto.ts` следует RFC 8785 (JSON
Canonicalization Scheme): порядок ключей по кодовым единицам UTF-16, свойства
со значением `undefined` опускаются (как их опускает передача через JSON), а
значения, которые JSON не может передать, вызывают `TypeError` (`undefined` в
массиве, не конечные числа, `bigint`, функции, символы, не простые объекты
вроде `Date`, `Map` и типизированных массивов, одиночные суррогаты). Эталонные
векторы находятся в `canonical-v2.test.ts`.

**Маркер.** Подпись над байтами v2 начинается с `c2.`; дальше идёт обычная
подпись Ed25519 в base64url. Её создаёт `signCanonical`, а `verifyCanonical` и
`canonicalSigned` выбирают по ней байты:

- маркер `c2.` есть — проверка по байтам v2;
- маркера нет — проверка по байтам v1, поэтому объекты, подписанные и
  сохранённые до v2, остаются действительными. Новые подписи по v1 не
  создаются.

Маркер находится вне подписанных байтов. Перестановка маркера ничего не даёт
атакующему: подпись v2, проверенная как v1 (или наоборот), сходится только
когда обе сериализации совпадают побайтно, то есть это одно и то же значение
JSON. Значение, которое v2 не может представить, проверяющий отклоняет, а для
подписывающего это ошибка.

**Что использует v2.** Все подписи, которые создаёт Core: транспортные
конверты и доменно-разделённые подписи identity, социальные объекты,
сообщения, сообщества, spaces, публикации, календарь, задачи, vaults, общие
папки, device mesh, манифесты delay-tolerant parcel, протоколы агентов и
подписывающий хост desktop.

**Что намеренно остаётся на v1.** Всё, что является идентификатором или
связанными данными, а не подписью: хэши действий, id контента, integrity
digest, отпечатки, associated data для AEAD и сравнения. Эти значения уже
сохранены или разосланы, смена их байтов сделала бы их недостижимыми; для них
действуют свойства v1, описанные выше. Подписи репликации контактов остаются
на собственном сериализаторе v1 (`contacts.ts`), который уже опускает
`undefined`. Перевод любого из них требует отдельного версионированного
идентификатора, а не замены сериализатора.

**Совместимость.** Сборка без v2 отклоняет подпись с `c2.` (это не корректный
base64url), то есть отказывает, а не читает её неверно; в смешанной установке
сначала обновляются проверяющие, затем подписывающие. Срока прекращения приёма
подписей без маркера пока нет: у сохранённых объектов v1 нет пути
переподписания.
