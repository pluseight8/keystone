# Localization / Локализация

Keystone currently supports English (`en`) and Russian (`ru`). The selected language is a user preference, never a network-wide setting and never part of a signed social object. Peers retain their own display language while exchanging language-neutral identifiers, timestamps, metadata fields, and signatures.

The shared setting writes `keystone.locale`. `I18nManager` loads that preference before falling back to platform language detection and emits a change event. Shared settings and mobile surfaces subscribe to that event. The web development shell uses the same persisted preference and synchronizes its local UI subscribers.

New user-facing UI must provide both translations at the time it is introduced. Protocol vocabulary (`keystone://` URIs, object types, capability names and signed payload field names) stays stable and English-only because changing it would change the signed wire format. Product documentation may retain an English canonical page alongside a Russian companion; security-sensitive code and protocol snippets must not be translated in a way that changes their meaning.

Russian product copy uses natural, consequence-oriented words. Preferred terms
include «Подключение», «Локальная сеть», «Мэш-сеть», «Ретранслятор», «Шлюз»,
«Отложенная доставка», «Синхронизация», «Хранилище», «Дополнение»,
«Разрешения», «Центр безопасности», «Локальный ИИ», «Уведомления» and
«Качество соединения». Do not translate or transliterate stable technical
identifiers such as Keystone, Hyperswarm, Noise, WebRTC, Wi-Fi Direct,
`ConnectivityFabric`, object types or capability names. Use «Сеть Keystone» for
the broad product network and «Мэш-сеть» only for the routing concept.

Settings and error messages should say what the user can do next. Avoid
unexplained technical switches, awkward literal transliterations, and wording
that implies a hosted account or mandatory cloud.

## Русский

Keystone поддерживает английский (`en`) и русский (`ru`). Выбранный язык — это локальная настройка пользователя, а не настройка сети; он не попадает в подписываемые социальные объекты. Устройства могут показывать интерфейс на разных языках, обмениваясь при этом независимыми от языка идентификаторами, временными метками, метаданными и подписями.

Общая настройка сохраняется в `keystone.locale`. `I18nManager` сначала читает её, затем использует язык платформы и оповещает подписчиков об изменении. Настройки, mobile-интерфейс и web-соболочка подписываются на это изменение.

Новые пользовательские экраны должны появляться сразу на обоих языках. Элементы протокола (`keystone://` URI, типы объектов, имена возможностей и поля подписываемых payload) остаются стабильными и английскими: их перевод менял бы формат обмена. Английская документация остаётся канонической, а для материалов социальной и медиа-подсистемы доступен русский обзор ниже.
